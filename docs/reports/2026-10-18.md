## R1 — the disc step asks twice

> "launcher when u press on choose disk it moves u to the old choose disk menu and u gotta press choose disk again.
> Kind of a waste. Why not make me choose disk on the first prompt. Like u press choose disk on launcher and then i
> choose the disk on the file browser."

**Measured:** not yet reproduced here (no device). Code reading says the two screens are two different things:
the launcher's own disc step draws its own "choose disc" button (`src/app/main.c`, the wizard/front-end loop), and
the OS picker is `DiscActivity` — which the *launcher* now starts through `plat_pick_disc` (`src/platform/android/android_host.c`),
while `GameActivity.onCreate` also starts `DiscActivity` when it holds no descriptor
(`android/app/src/main/java/org/moonengine/android/GameActivity.java:28-36`). Two owners of the same picker is the
obvious candidate for "asked twice", and it is the same wiring that R2 lands on.

**Status:** OPEN (device reproduction wanted: does the second screen appear before or after the engine boots the game?)

**Fix (this build):** the double prompt was one screen asking twice, not two activities. In picker mode
`DiscActivity` drew its own CHOOSE button and only then opened `ACTION_OPEN_DOCUMENT`, so the launcher's single
"choose disc" cost two taps. In picker mode it now posts straight to the system file browser (`launchPicker()`);
the launcher is the only owner of the picker, and `GameActivity.getArguments()` reuses the held descriptor without
prompting again. Not yet confirmed on the A34 (no device here).

## R2 — choosing the disc crashes the app, and it now crashes on every start (A34)

> "wow. The moment i chose disk the app just crashed and everytime I press on it it crashes. Refuses to work. This
> is on A34. what do you think is the culprit?"

**Measured / candidate causes, ranked — none confirmed yet, no logcat has been read:**

1. **The movie path is brand-new on Android in this very build.** `cd518b9` links libav into `libmain.so` for the
   first time and `src/platform/sdl/movie.c` takes the in-process route on Android; before this commit Android
   compiled the stub (`movie.c:424`) and simply had no movies. The first thing a chosen disc triggers is the intro
   /menu movie → the first place a brand-new decoder can die. **This is the leading hypothesis.**
2. **The descriptor may live in the wrong owner.** `plat_pick_disc` runs in the launcher's native side, while
   `GameActivity` re-opens the saved `startup/discUri` and passes `/proc/self/fd/<n>` as `argv[1]`
   (`GameActivity.java:11-17`). If the launcher's pick and the activity's pick are two different descriptors, the
   engine can be handed a stale fd — which would explain both "crashed the moment I chose" and "crashes every start"
   once a URI is saved (same wiring as R1).
3. **The touch change (`ef3ba38`)** is one file and 24 lines in `main.c`; it is not impossible but far less likely to
   crash a boot than a decoder or a file descriptor.

**The A/B that settles 1 vs 2/3, without the device:** an APK built from the commit *before* these two
(`606040a`, overlay only) is published beside the current one. If the old one boots and the new one does not, the
cause is in this build's diff; if both crash, it is older than today's work.

**What is needed to see the actual cause:** the app's own log (`files/moonengine.log`) or `adb logcat -s moonengine SDL`
— both need ADB. **Wireless debugging on the A34 once would let me read the crash myself** instead of guessing.

**What this build adds (no device here, so not reproduced):**
- A kill switch that proves or kills suspicion 1 without a rebuild: `MOON_NO_MOVIES=1` in the environment, or an
  empty file `no-movies` in the user root (`Android/data/org.moonengine.android/files/MoonEngine/MoonEngine/`, the
  reachable root this build moves to). With movies off, every MovieFace falls back to the authored poster — if the
  app then boots, the crash is the decoder; if it still crashes, it is not.
- A fatal-signal handler (SIGSEGV/SIGABRT/SIGBUS/SIGFPE) that writes one final, fsync'd line to
  `<user root>/moonengine.log`, `fatal: signal <n>, last frame <file:line>`, naming the last decode step the movie
  path marked, then re-raises so Android still records it. The log now lives on external storage and is mirrored
  to `Download/MoonEngine/moonengine.log`, so it can be attached without ADB.
- Code review of the in-process path found no Android-only defect I can point at: the AVFilter graph is CPU-only
  (no GL context needed), the custom AVIO seek/read contract is within bounds, libav is read from a full in-memory
  copy of the `.pss` (not the disc adapter), and the frame copy is 640x448 RGBA as the filter chain forces. The one
  real Android difference is timing, not correctness. The fatal line is the honest next step.

**Status:** OPEN (kill switch + crash line shipped; the decoder is still the leading suspect, unproven)

## R2 — RESOLVED TO A CAUSE: the log he sent names it (2026-10-18, later)

**My movie hypothesis was WRONG.** He attached `moonengine.log`, and it reads:

```
moonengine: user root=/storage/emulated/0/Android/data/org.moonengine.android/files/MoonEngine/MoonEngine/ …
launcher: studio front-end (arguments 6)
Vulkan renderer: Mali-G68 MC4
launcher: touch-mouse synthesis on
Vulkan presentation failed: surface capabilities: -1000000000      ← VK_ERROR_SURFACE_LOST_KHR
launcher: touch-mouse synthesis off
…
launcher: game (arguments 8)
cannot open a window: Android only supports one window              ← the crash, every start
```

- **Three pieces of tonight's work are confirmed working on the device:** the shared user root + mirror line, the
  no-argument launcher start (`studio front-end`), and the touch fix (synthesis on, then off at handover).
- **The fault is window/surface lifetime, not decoding.** The launcher's Vulkan surface is **lost**
  (`-1000000000` = `VK_ERROR_SURFACE_LOST_KHR` — what an Android activity handover does to a surface), and the
  handover then tries to open **a second window**, which SDL refuses by design
  (*"Android only supports one window"*). `main()` returns and the process dies — which is exactly "crashed the
  moment I chose the disc", and with a URI now saved, every later start takes the same road.
- **The decoder is exonerated:** nothing in the log points at libav, so `no-movies` is not needed for this bug.
- **The two fixes are concrete:** (1) exactly ONE SDL window for the app's lifetime — reuse the launcher's window
  for the game (or destroy it before the game's is created); (2) recover a lost surface (recreate surface +
  rebuild swapchain) instead of failing presentation when the picker or a background/foreground cycle kills it.

**Status:** PROMPTED `moon-window` (recipe `/home/or/.hermes/recipes/moon-android-window.txt`)
